# 工作日志 (Journal)

按时间线记录项目重要阶段的决策、改动和结果。面向人阅读，是项目记忆的主干。

## 定位

项目有四层文档，各自职责不重叠：

| 层级 | 位置 | 内容 | 谁写/何时写 |
|------|------|------|------------|
| **工作日志** | `docs/journal/` | 做了什么、为什么、结论 | 每个 PR 合并或里程碑完成时 |
| **PR 描述** | GitHub PR body | 本次合并的技术改动与验证 | 创建 PR 时 |
| **任务笔记** | `tasks/*/NOTES_*.md` | 单任务的操作细节、调试过程 | 执行过程中随手记 |
| **参考文档** | `docs/*.md` | 架构、契约、方法论 | 需要时更新 |

## 命名规则

```
docs/journal/YYYYMMDD_{slug}.md
```

- 日期为该阶段**完成**日期
- slug 用小写英文短横线连接，概括主题
- 一个日志条目可以覆盖多天的工作

## 条目结构

```markdown
# {标题}

> PR: #{num} | 分支: `{branch}` | 时间跨度: YYYY-MM-DD → YYYY-MM-DD

## 背景

为什么要做这件事。1-3 句话。

## 关键决策

- 决策 1：选了 A 而不是 B，因为 ...
- 决策 2：...

## 改动摘要

按模块列出主要改动，不需要逐文件，重点是 **读者能理解整体轮廓**。

## 验证与结果

量化结果、关键数字、是否符合预期。

## 遗留与后续

- [ ] 待办 1
- [ ] 待办 2

## 相关文档

- `tasks/xxx/NOTES_YYYYMMDD.md`
- `docs/xxx.md`
```

## 与 PR 的关系

```
工作日志条目  ←1:1 或 1:N→  PR
```

- 小 PR：合并后在日志中一句话记录即可
- 大阶段（如本次整理提交）：一个日志条目覆盖多个 PR，PR 描述引用日志条目
- PR 描述中加一行 `📓 Journal: docs/journal/YYYYMMDD_slug.md` 建立双向链接
